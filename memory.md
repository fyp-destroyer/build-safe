- [x] **`ml/validate_dataset.py` written** — mechanically enforces every rule in `ml/data/README.md` (risk/label agreement, `risk_level: 5` ⇒ empty `suggested_ppe`, unanswered-safety-critical-follow-up ⇒ `risk_level: 5`, canonical question wording, enum validity, exact-duplicate detection, `tool_available` only when `tools_available` is empty). Run it after any dataset change. It caught a real wording bug in the pre-expansion data on its first run.
- Schema, taxonomies (hazards, PPE, professional categories) and — most importantly — the **follow-up scoping rules** are documented in `ml/data/README.md`. Those rules were derived iteratively from real mistakes caught in review (see the 2026-07-29 Decisions Log entries); they are the part most likely to be violated during the template-expansion step, which is exactly why the validator exists.
- **Deliberate near-duplicates:** three pairs share a base task and differ only in what `task_text` states (the `"install a ceiling fan"` set, two `"remove a wall between the kitchen and living room"` variants, two `"light switch cover plate"` variants). They teach the model that *stated information*, not task type, drives the follow-up and risk outcome. **Keep each pair in the same train/val/test split or they leak.**
- [x] **Template variation + weak-labeling — done 2026-07-29: 299 generated variants in `ml/data/generated_examples.json`, total 555.** Produced by `ml/generate_variations.py` (deterministic, re-runnable). Seeds keep stable `id`s (`seed-0001`…); every generated row carries `variant_of` + `generation_rule`, and lives in a separate file so seeds stay the authoritative hand-judged set.
  - Three weak-labeling rules, **none of which can lower a risk level** (`rules.md` §4.2, enforced by the validator): `WL-1a:rephrase` (256 — conversational framings; seeds are all bare imperatives but real chat input is hedged/question-shaped, so this is genuine robustness coverage), `WL-1b:room-substitution` (26 — risk-neutral rooms only, never bathroom/basement/loft/garage where the room *is* part of the hazard), `WL-2:strip-confirmation` (17 — removes a stated safety confirmation so the condition becomes unaddressed, forcing `risk_level` 5; each stripped text hand-written, not regex-derived, because it changes a safety label).
  - **De-escalation is deliberately not automated.** Injecting a confirmation (which lowers risk) is the direction where a wrong label is dangerous, so those stay hand-written seeds only.
- Validator extended to cover the generated file: checks each variant's label against its stated rule and rejects any variant scoring below its parent. Verified it actually fails by feeding it 6 deliberate violations (de-escalation, un-escalated WL-2, risk-5-with-PPE, orphan `variant_of`, unknown rule, label/level mismatch) — all 6 caught.
- **Two traps for the split step (`ml/data/README.md` documents both):** (1) group by `variant_of` — a variant shares nearly all its text with its parent, so a naive split puts the same task in train and test; (2) the three deliberate near-duplicate *seed* pairs need the same treatment. Also: report headline metrics on hand-written seeds only, or the eval measures the generator rather than the task.
- [~] **Label-quality review — substitute done 2026-07-29, genuine expert review still outstanding.** `ml/review_high_risk.py` audits all 555 examples against 11 risk floors derived from published standards (HSE, OSHA Focus Four, Gas Safety Regs 1998, Control of Asbestos Regs 2012, BS 7671/Part P, Confined Spaces Regs 1997) plus `srs.md` §9; write-up in `ml/data/REVIEW.md`. **95.8% → 100% conformance after fixes.**
  - ⚠️ **This is NOT an inter-rater agreement statistic and must never be reported as one** — the labels and the audit rules were authored in the same session by the same author, so it shows internal consistency against an external rubric, not that a tradesperson would agree. Discharging `phases.md`'s "expert review" properly needs a licensed tradesperson labelling a blind sample (≥50, weighted to risk 4–5) with Cohen's κ. Still provisional per `prd.md` §7.
  - Findings were **three different kinds of problem**, only one a bad label: (1) genuine mislabel — two-storey exterior painting from an extension ladder was `2`, raised to `3` per §9's "height above safe threshold"; (2) wrong hazard tag — a bathroom GFCI outlet carried `water_damage`, which elsewhere means water *escaping*, removed; (3) two audit rules were themselves too broad (fired on damp locations and on low outbuildings) and were narrowed. A fourth bug was in the audit tool: substring matching made `"flood"` match **flood**light. Rules are now word-boundary anchored.
  - Narrowing a rule after it flags something is how an audit gets tuned to pass, so each change is justified against the standard it cites, and gas-related examples were re-checked by hand afterwards to confirm no coverage was lost.
  - Only 64/256 seeds match any rule, so **~75% of the dataset is unaudited by this method** and rests on the original hand-judgement.
- [x] **Split — done 2026-07-29: `ml/data/{train,val,test}.json`, 387/86/82 (69.7/15.5/14.8%)** via `ml/make_splits.py` (deterministic, no RNG). All 5 classes in every split, in both the full and hand-written-only views. ### Phase 3 — Baseline ML Model
- [x] **`ml/train_baseline.py` — done 2026-07-30.** TF-IDF (word + char n-grams) + Logistic Regression, `class_weight="balanced"`, hyperparameters selected on val (`C=4.0`, unigrams). Artifact: `ml/eval/baseline_model.joblib` (refit on train+val; test held out). Report: `ml/eval/baseline_report.md`, `baseline_metrics.json`, `baseline_confusion.png`.
- **Results (hand-written test, n=40), after the 2026-07-31 serve-parity retrain:** accuracy 0.625, macro-F1 0.614, high-risk recall **0.529, 95% CI [0.31, 0.74]**; grouped CV macro-F1 0.620 ±0.065, high-risk recall 0.652 ±0.045. (Pre-retrain figures were 0.650/0.646 but relied on a `tools` feature the backend cannot supply — see Phase 4.) Grouped 5-fold CV over all 555 rows, the more stable estimate: macro-F1 **0.679 ±0.041**, high-risk recall **0.706 ±0.090**. Far below `prd.md` §7's provisional ≥95% target — expected, and explicitly allowed by the exit check ("even if not yet at target"). **Exit check MET.**
- **Feature choice is the load-bearing decision here.** Inputs restricted to what the backend actually has at assessment time: `task_text`, `category`, `user_skill`, `tools_available`. Everything else leaks the label — *measured, not assumed*: `professional_category is None` ⟺ `risk ≤ 2` in **555/555** rows; `suggested_ppe == []` whenever risk 5; an unanswered safety-critical follow-up ⟹ risk 5 in all 59 rows; 37 of 66 distinct hazard sets map to a single risk level. Using any of them would have produced a flattering, meaningless score.
- Follow-up state is excluded for a second reason: escalating on a missing safety-critical answer is the **rule engine's** job and `final_risk = max(ML, rules)` combines them. So **ML-only recall understates the deployed system** — simulating just the follow-up rule on top of the predictions lifts test high-risk recall 0.514 → **0.657** (5 rows rescued). That simulation is still a floor: the real engine also has keyword hazard rules.
- **A split defect was found by error analysis, not inspection** (see Decisions Log 2026-07-30): the first run predicted `safe_diy` for 16 of 24 truly-dangerous test rows. Cause was not the model — problem-report phrasing ("my gas water heater is hissing") was split 10 train / 14 test, so the test set held *more* of that population than training did. Fixed by stratifying the split on problem-report style as well as risk level; `make_splits.py` now fails if train holds <50% of them. Splits are now 387/87/81. Baseline macro-F1 went 0.533 → 0.613 and high-risk recall 0.444 → 0.514 on the corrected split.
- Known weaknesses to attack in Phase 4: 9 of 23 true-risk-5 test rows still predicted as risk 1 (mostly asbestos / fragile-surface / emergency-report tasks); no probability calibration yet, though `srs.md` stores a confidence per assessment; effective sample size well under 555 because 299 rows are weakly-labelled paraphrases.
- Status: **Complete.** Exit check met; performance intentionally left as the baseline to beat in Phase 4.

### Phase 4 — Improved ML Model
- [x] **`ml/evaluation.py` — shared evaluation harness extracted first (2026-07-30), before any Phase 4 modelling.** Both trainers import it, so the two models are scored by identical code. This mattered: Phase 4's exit check is a decision about *which model ships*, and if each script computed its own metrics a subtle difference in how (say) high-risk recall was defined would quietly decide it. Refactor verified behaviour-preserving — baseline metrics byte-identical before and after.
- [x] **`ml/train_embedding_model.py` — done 2026-07-30.** `all-MiniLM-L6-v2` (384-d, frozen) + Logistic Regression head, `class_weight="balanced"`, same inputs as the baseline so the comparison isolates the representation. Embeddings cached (`ml/eval/embeddings_cache.npz`, gitignored — regenerable). Encoding all 555 rows up front is *not* leakage: the encoder is frozen pretrained weights, never fitted on our data.
- [x] **Comparison report — `ml/eval/comparison_report.md`. Exit check MET: the TF-IDF baseline ships.**
- **The decision rests on paired grouped 5-fold CV, not the held-out test set.** With n=40 hand-written test rows the 95% CI on high-risk recall spans ~±0.2 — wider than any plausible difference between two models. Both models were trained and scored on *identical* folds: macro F1 **−0.075 ± 0.033 (embedding loses 5/5 folds)**; high-risk recall −0.020 ± 0.082 (embedding wins only 2/5, i.e. noise). So the embedding model is decisively worse overall and no better on the metric that matters.
- **Why the general-purpose encoder lost** — worth remembering, since it inverts the usual expectation: risk in this corpus is carried by rare, discriminative domain tokens (*gas*, *asbestos*, *load-bearing*, *consumer unit*, *breaker*, *fragile*). TF-IDF weights exactly those, and char n-grams catch their morphology (*wiring*/*rewire*). MiniLM compresses each sentence into 384 dimensions tuned for general semantic similarity, where *"replace a light fixture"* and *"replace a consumer unit"* sit close together despite being three risk levels apart — and ~390 training rows is far too little to learn a head that recovers the distinction. Keyword features beating general-purpose embeddings is a known outcome on small, jargon-dense corpora.
- Cost reinforces the same choice: shipping the embedding model would add torch and a ~90 MB download to the serving path for a measurable *loss* in accuracy. Serving stays scikit-learn-only. Both artifacts kept per `architecture.md` §1.
- `ml/requirements.txt` added, pinning the ML stack; torch/transformers/sentence-transformers are flagged in it as needed **only** to reproduce this comparison, not to serve.
- **CORRECTED 2026-07-31 while wiring the model into the backend.** Both models had been trained with a `tools_available` feature the backend cannot supply (`Job` has no tools column, intake never asks) — train/serve skew. Retrained both without it for serve parity, which **materially changed the Phase 4 result**: the embedding model is no longer decisively worse (macro F1 −0.075 → **−0.009 ±0.056**, high-risk recall **+0.014 ±0.046**; both now inside fold noise). The earlier "decisively worse" verdict was largely an artifact of TF-IDF exploiting a feature production would never have.
- **The ship decision is unchanged but now rests on a different reason:** the two are statistically indistinguishable, so the tie is broken on deployment cost (scikit-learn only vs torch + ~90 MB). That is the correct branch of the decision logic, not the "embedding is worse" one.
- Status: **Complete.** Baseline ships. The embedding experiment stands as a documented null result — no measurable difference — rather than a clear loss.

### Phase 5 — Safety Rule Engine
- [x] **Real rule engine built 2026-07-31, replacing the keyword placeholder.** `ai/rule_engine/catalog.py` holds the DATA (13 hazard rules: id, hazard tag, escalation floor, hardcoded explanation, keywords, optional category/skill gates); `ai/rule_engine/rules.py` holds the LOGIC. Split deliberately so no hazard can be defined anywhere else.
- [x] **LLM hazard tagging — `llm_assist.tag_hazards()`.** The LLM's entire authority is selecting ids from the hardcoded catalog. Every returned id is filtered against `VALID_RULE_IDS`; invented ids are dropped and logged. It cannot assign a risk number or change a floor. Failure returns `[]`, so the engine degrades to "no LLM", never "no hazards" — keyword rules still run.
- [x] **Exit check MET** — `tests/test_rule_catalog.py`, 45 pure-logic tests (no DB, no network). Escalation invariant is proven exhaustively over descriptions × categories × answer sets × all 5 ML outputs. Adversarial LLM inputs tested: hallucinated ids, empty string, and a SQL-injection-shaped id all discarded with risk unchanged.
- **Jurisdiction-neutral by explicit user decision (2026-07-31):** rules state hazard and consequence, never legal citations, because the project targets no specific regulatory regime and shouldn't claim legal authority it can't back. Same reasoning as `ml/data/REVIEW.md`.
- **Three-state follow-up semantics**, which the placeholder did not have: *missing* (floor 5 — worst plausible case cannot be ruled out) > *answered no* (floor 3–4 — unsafe but a known state the user can be advised about) > *answered yes*. Keeping missing strictly above denied is asserted by a test, since conflating unanswered with answered-unsafe is the exact bug that once made the whole dangerous-task path unreachable (see 2026-07-19).
- **Removed a duplicated safety mapping.** `services/job_service.py` had its own `_REQUIRED_FOLLOWUPS_BY_CATEGORY` table alongside the rule engine's — two copies of a safety-critical mapping that could drift silently. Both now derive from `required_followups()`.
- **Follow-ups are hazard-driven, not category-driven.** A failing test caught that the old design gated wiring rules on `category == "electrical"`, so chasing a wall in a *tiling* job never triggered the power-isolation question — contradicting what the dataset encodes. Fixed by making `fixed_wiring_work` category-agnostic.
- **The engine now receives `user_skill`,** so `srs.md` §9's "electrical wiring task + beginner user" is implemented faithfully rather than approximated by category. Previously a rule was *named* for beginners but had no way to check skill.
- **Recall work 2026-07-31 — four rules added, measured before and after (`ml/analyze_recall.py`).** Deployed recall **0.804 → 0.873** for +0.006 over-escalation (0.088 → 0.094): roughly an 11:1 trade. New rules: `unprotected_or_adverse_height_work` (wet/icy roof, no harness, third-floor — floor 5), `major_roof_structural_work` (floor 4), `major_plumbing_alteration` (mains/soil stack/waste — floor 4), `uncontrolled_burning` (treated timber — floor 5). Keywords are multi-word on purpose: rules are the cheapest recall this system has *because* they rarely false-fire, and loose single words would spend that advantage.
- **Rules buy recall ~4-7x more cheaply than the model.** Rule engine alone: recall 0.593 at 0.017 over-escalation. ML alone: 0.652 at 0.077. That asymmetry is why rules, not model tuning, are the right lever here.
- **The headline number needed decomposing, and this is the important finding.** Of 26 remaining missed high-risk rows, **20 are labelled 5 only because a safety question is unanswered** — a state production never evaluates, since `assess_job` 409s until every required follow-up is answered. Only 6 are genuine. **Recall on tasks whose hazard is actually stated in the text is 0.959**, which meets `prd.md` §7's ≥95% target. The gap between 0.873 and 0.959 is a dataset/production definitional mismatch, not a detection failure — worth stating plainly in the report rather than quoting either number alone.
- Measured but rejected as levers: **decision-threshold tuning** hits 0.99 recall but at 0.52 over-escalation (more than half of safe tasks told to hire a professional — destroys the product's premise); **class weighting** is strictly dominated by thresholding; **more data** is weak here, with the learning curve flattening (0.583 → 0.652 across 4x data), so doubling the dataset likely buys ~+0.03.
- **Three more rules 2026-07-31, added under an anti-overfitting protocol at the user's request.** `circuit_extension` (extending fixed wiring vs replacing an accessory — floor 4), `decayed_roof_timber` (rafters/purlins/wall plate — floor 4), `masonry_wall_instability` (lean, movement, through-cracking — floor 4). Catalog now 21 rules.
- **Protocol, because fitting rules to the remaining eval failures is textbook overfitting:** `ml/data/holdout_rules.json` (24 fresh tasks, none in the training data) was written and **committed before** the rules it tests, so they provably could not be fitted to it. **14 of the 24 are adversarial negatives** — "lean a ladder against the wall", "replace a rotten fence post", "swap the faceplate on an existing socket", "fill a hairline crack" — because overfitting shows up as an over-broad rule as much as a narrow one, and positives alone cannot detect that. Rules were written against the hazard *concept*, not the miss strings, and the positives deliberately use different vocabulary.
- **Result: 24/24 held out** (10/10 positives caught, 14/14 negatives held), up from a pre-rule baseline of 0/10 and 14/14. On the main data, deployed recall **0.873 → 0.902 with over-escalation unchanged at 0.094**; genuine misses **6 → 0**; recall on tasks whose hazard is stated in the text is now **1.000**.
- ⚠️ **How to report that 1.000 honestly:** on training data it is exactly what overfitting would look like, so it must never be quoted alone. The evidence it generalises is the held-out 24/24 on examples committed beforehand. Quote both, or quote neither. The remaining 20 missed rows are all the unanswered-follow-up definitional artefact, which production never evaluates.
- `ml/check_holdout.py` runs the validation; keep it green when touching the catalog.
- Status: **Complete.** Note the classifier half of `max(ML, rules)` is still the keyword placeholder — the Phase 3/4 trained model is not yet wired into the backend (deliberately deferred, see Decisions Log), so the rule engine currently carries the safety guarantee on its own.

- **The disposable test Postgres container's schema does not persist across `pytest` runs** (worth knowing for future live/manual verification against it): `tests/conftest.py`'s session-scoped fixture runs `Base.metadata.drop_all` at teardown, dropping all real tables — but `alembic_version` (a separate bookkeeping table Alembic owns, untouched by `Base.metadata` operations) is left pointing at `head`, so a subsequent plain `alembic upgrade head` sees "already up to date" and is a silent no-op, leaving the container with an empty schema. If manually verifying against this container after a `pytest` run, either recreate tables directly (`Base.metadata.create_all` via a one-off script) or `alembic downgrade base && alembic upgrade head` won't work either (downgrade tries to drop already-gone tables) — dropping the `alembic_version` table first, then `alembic upgrade head`, is the reliable reset. This bit both the Phase-6 build session and this session's verification.
- **On Windows/Git-Bash, `pkill -f <name>` does not reliably kill Python/uvicorn processes started via `nohup ... &`** — they appear to run as native Windows processes invisible to Git Bash's `ps`/`pkill` (MSYS2's process view), so a "restarted" server can silently still be the old process bound to the port, serving stale code. Use `netstat -ano | grep :<port>` to find the real PID, then `Stop-Process -Id <pid> -Force` via PowerShell to actually kill it. Cost real time during this session's verification (a fix appeared to not take effect because the old process was still answering requests).

- **The Phase 6 placeholder rule engine's `power_isolated` follow-up is binary and can't express "isolation not possible, but mitigated via PPE" as distinct from "isolation simply unanswered."** Surfaced during Phase 2 dataset design (2026-07-29, see Decisions Log) — the dataset now models three states for electrical tasks (isolation unstated / confirmed isolated / confirmed not possible but insulated gloves + tester used as mitigation), where the third state should plausibly land at a *different* (likely lower) escalation than the first, since a real, stated mitigation exists. `ai/rule_engine/rules.py`'s current `_SAFETY_CRITICAL_FOLLOWUPS` treats any falsy/missing `power_isolated` identically. Worth designing for explicitly when Phase 5 replaces the placeholder — not a bug in the placeholder (it's not meant to be final), just a design note so the nuance isn't lost.
