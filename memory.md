Manually read `ai/rule_engine/rules.py` and `services/job_service.py` end-to-end: confirmed `final_risk = max(...)` is enforced for real, missing safety-critical follow-ups block `/assess` with 409 rather than silently proceeding, and AI pipeline exceptions are caught and written to `ai_logs` + `RiskAssessment.status="failed"` (risk_level defaults to 5, the worst plausible case) rather than defaulting to a "safe" result.

- **LLM layer added (2026-07-19), Google Gemini API, replacing the planned Anthropic API** (user's explicit choice — see Decisions Log): `ai/llm/client.py` (`generate_structured`, schema-constrained JSON output, never raises, returns `None` on any failure) and `ai/rule_engine/llm_assist.py` (`tag_category` — infers one of the 9 fixed `TASK_CATEGORIES` from free text, hard-validated against the fixed set, falls back to `"general"`; `phrase_followup_question` — phrases wording for an already-hardcoded follow-up field, falls back to a hardcoded default phrasing). Both functions have zero influence over risk level, rule triggering, or which fields are required — rules.md §4 boundary verified by a dedicated test forcing a hallucinated/out-of-set category response and confirming the "general" fallback fires. `JobCreateRequest.category` is now optional (backend infers it when omitted); `JobOut` gained a computed `next_followup: {field, question} | None`. `GET /jobs` (list current user's jobs, most recent first) added for the frontend sidebar.
- **Safety-critical bug found and fixed during live end-to-end verification (2026-07-19), not caught by the 36 tests that existed at the time:** `job_service._missing_required_followups` used `not job.followup_answers.get(field)` (truthiness) instead of presence, so an *explicitly answered* `False` (e.g. "No, I have NOT confirmed the gas line is absent" — an honest, safety-critical answer) was treated identically to "never answered at all." This made `POST /jobs/{id}/assess` return 409 forever for any job where a safety-critical answer was honestly "no" — meaning the entire Dangerous/Do-Not-Attempt demo-scenario path (the whole point of a chunk of the product) was unreachable through the real API; a user could never get any risk assessment for such a task, only a permanent block. `ai/rule_engine/rules.py`'s own escalation logic was already correct (falsy-or-missing → escalate) and completely unreachable because of this earlier gate. Root cause: conflating "unresolved" with "resolved-but-unsafe." Confirmed against srs.md's own exception-flow wording, which distinguishes the two. **Fix:** `_missing_required_followups` now checks field *presence* in `followup_answers`, not truthiness; `create_job` now applies the same status-transition logic `submit_followup` already had, so a zero-followup-required job (e.g. category `"general"`) starts at `"ready_to_assess"` immediately instead of a misleading `"pending_followup"`. Verified live end-to-end post-fix: an honestly-answered "gas line present" job now correctly reaches a real `risk_level: 5` assessment instead of 409ing forever. Two tests updated/added in `tests/test_job_flow.py` (`test_explicit_false_followup_answer_unblocks_and_escalates_risk` is the regression test — asserts `risk_level >= 4` and that `missing_followup:power_isolated` actually appears in `triggered_rules`, not just that assess "succeeds"). Also fixed a minor, non-safety cosmetic bug found alongside it: `ai/rule_engine/rules.py`'s `evaluate()` could report the same rule name twice (two keyword rules matching the same hazard, e.g. "gas" + "gas leak" both → `gas_hazard`) — now de-duplicated (order-preserving) before returning `triggered_rules`.
- Full suite: 38/38 pytest passing, ruff + black clean, independently re-verified by the supervising session (not just trusting agent self-reports) after every change including the safety-gate fix above.

If manually verifying against this container after a `pytest` run, either recreate tables directly (`Base.metadata.create_all` via a one-off script) or `alembic downgrade base && alembic upgrade head` won't work either (downgrade tries to drop already-gone tables) — dropping the `alembic_version` table first, then `alembic upgrade head`, is the reliable reset. This bit both the Phase-6 build session and this session's verification.
- **On Windows/Git-Bash, `pkill -f <name>` does not reliably kill Python/uvicorn processes started via `nohup ... &`** — they appear to run as native Windows processes invisible to Git Bash's `ps`/`pkill` (MSYS2's process view), so a "restarted" server can silently still be the old process bound to the port, serving stale code. Use `netstat -ano | grep :<port>` to find the real PID, then `Stop-Process -Id <pid> -Force` via PowerShell to actually kill it. Cost real time during this session's verification (a fix appeared to not take effect because the old process was still answering requests).

- **The Phase 6 placeholder rule engine's `power_isolated` follow-up is binary and can't express "isolation not possible, but mitigated via PPE" as distinct from "isolation simply unanswered."** Surfaced during Phase 2 dataset design (2026-07-29, see Decisions Log) — the dataset now models three states for electrical tasks (isolation unstated / confirmed isolated / confirmed not possible but insulated gloves + tester used as mitigation), where the third state should plausibly land at a *different* (likely lower) escalation than the first, since a real, stated mitigation exists. `ai/rule_engine/rules.py`'s current `_SAFETY_CRITICAL_FOLLOWUPS` treats any falsy/missing `power_isolated` identically. Worth designing for explicitly when Phase 5 replaces the placeholder — not a bug in the placeholder (it's not meant to be final), just a design note so the nuance isn't lost.
